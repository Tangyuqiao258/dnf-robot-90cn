# 90CN 适配笔记（服务端契约）

本文记录适配 90CN（DNF90 一键工程 Go 服务端）时从服务端源码确认的关键契约，供后续阶段（持久化、装备、摆摊、实机联调）使用。服务端源码位于 `DNF-90CN.git` 的 `DNF90-source-oneclick/go-server`（模块 `longheng.io/server`）。

## 运行布局与配置

- 工程根目录包含 `go-server/` 与 `runtime/`；机器人配置的“服务端目录”可指向工程根目录或 `runtime` 目录。
- 权威实例配置：`runtime/config/instance.json`（`server.channelListen`、`server.adminListen`、`server.adminToken`、`database.path`、`game.pvfPath`，均为 runtime 相对路径）。`runtime/configs/dnfbridge.toml` 是由控制端生成的服务端配置，含 `[service] public_addr`、`[admin] listen/token`、`[pvf] path`。
- 服务端监听：频道目录端口（`channelListen`，如 7001）与每个频道的 game 端口（实例 `client.gamePortBase` + `channel.ID`，本机基址 11000）；频道目录来自 `data/dnf/channel_info.etc`，普通/特殊频道按行的 area group（`[granfloris]` 普通、`[crack]`/`[pvp]`/`*raid` 特殊）区分，**type 列不能作为分级依据**（普通城镇频道 type 11，与旧 S4A21 的 type 表冲突）。连接必须落在目录内的 game 端口，否则直接断开。

## 账号绑定

- 登录器把“本机进程 PID → 账号 id”登记到管理端：`POST http://127.0.0.1:<adminListen>/local/client-account`，头 `X-Admin-Token: <adminToken>`，JSON `{"pid":<uint32>,"account_id":"<string>"}`，成功 204。
- 服务端在 accept 时用 `GetExtendedTcpTable` 解析 TCP 连接属主 PID，再查登记表得到 `session.accountID`（Windows、IPv4 环回）。未登记时回退到 `DNFBRIDGE_ACCOUNT_ID` 或 `dnf:1`。
- 账号 id 无存在性校验；`dnf_accounts`/`dnf_characters.account_id` 均用该字符串。机器人账号可使用 `robot<uid>` 形式。
- 机器人必须在**拨号前**登记，且登记与拨号之间不能被下一个账号覆盖；适配器用“登记 + 拨号 + 首个回包”一个临界区串行化。
- 登录账号表 `dnf_login_accounts`（bcrypt）只服务登录器/控制端，游戏协议不校验密码。

## 协议要点

- 出站：13 字节 legacy 帧（`cmd=1, u16 type, u32 length, u32 checksum(不校验), u16 seq`）。服务端分流器按 cmd/type/body 长度把 op1/op4/op5/op36/op1276 等重新归类为 raw upper；op8/op6/op692/op35 等走 legacy 分发。
- 入站：当前 profile `protocol.gameUpperHeader=server16`，raw upper 头 16 字节（`class(1) + msgID(2) + length(4) + checksum(4) + seq(2) + 3 reserved`），body 从 16 开始，解密为 plaintext；class0/op1 的 body 另有 XOR/ROT 编码（机器人可跳过 body）。
- 会话流程：连接 → （绑定会话）class0/op1 CHANNELINFO → class1/op1 请求（body 长度 590 或 598，内容不读）→ class1/op1 成功；未绑定会话直接收到 class1/op1 成功。
- 常用 opcode：op1 端点、op2 花名册（class0）、op3 退出（1 字节 body）、op4 选角（16 字节 `u32 slot + 12 零` 或 11 字节 charID 形态）、op5 建角（`u8 job + u32 nameLen + name + 8 应用选项字节`）、op6 删角（`u16 slot + u32 nameLen + name`）、op8 花名册请求（`00 00 02`）、op35 位置（7 字节）、op36 区域（16 字节）、op143 教程检查点（`u8 prefix=0 + u32 progress + u8 commit=1`，progress=36 触发初始城镇路线）、op692 查重（`u32 nameLen + name`）、op1276 心跳（空 body，选角后回 13 字节成功体）。
- 城镇：选角后服务端把角色登录位置写到 runtime PVF 的 Seria 门（town 38 / area 1）；op36 只在 `town_id` 相同或门户/传送形状时允许跨镇。op36 成功顺序：op22（USER_POSITION，9 字节 `u16 actorKey + u16 x + u16 y + u8 dir + u16 rate`）、op23（USER_AREA，10 字节 `u16 actorKey + u8 town + u8 area + u16 x + u16 y + u8 dir + u8 state`）、op356（完成任务位图，可选）、op24 场景转场（class0）。op35 只广播给同区域其他玩家（不落库、不回应）。
- 变成“对其他玩家可见”必须走 op36（`transitionTownPlayerPresence`）；初始城镇路线只建立本机场景。
- game 端口无读超时、无服务端主动 ping；op1276 在选角前不回包。

## 持久化要点

- 运行库为单文件 SQLite（`runtime/data/dnf90.db`，表前缀 `dnf`）。权威表是 `dnf_*` 原生表；`dnf_legacy_*` 是 C# 兼容镜像，只有少量读取回退（背包/称号簿、subtype0/1 尾部字段）。
- 主要表：`dnf_login_accounts`、`dnf_accounts`/`dnf_account_metadata`、`dnf_characters`（含 job/grow_type/level/exp/gold/town_id... 镜像列）、`dnf_character_stats`、`dnf_character_locations`、`dnf_inventories`/`dnf_inventory_items`（背包/个人仓库，`entry_key="<list>:<slot>"`）、`dnf_account_inventories`（账号仓库 354-365 槽）、`dnf_equipments`/`dnf_equipment_entries`（穿戴槽 0-13 外观、26 宠物、宠物神器）、`dnf_pets`/`dnf_pet_entries`、`dnf_quests`/`dnf_quest_states`（`state_group='states'/'progress'`）、`dnf_skills`/`dnf_skill_states`。
- 物品行有 `raw_entry`（若恰好 0x77 字节则作为客户端行基底）与 `*_extra` 键值（`raw_entry_hex`、`durability`、`seal_flag`、`expire_time`、`avatar_ability_no` 等）；格子表（slot）必须落在已购买容量内。
- 穿戴装备/时装的机器人侧写法（与服务器初始装备同构）：`dnf_equipment_entries(entry_key=<槽位>, slot_index, item_id, raw_entry)`，`raw_entry` 为 43 字节摘要（`slot, itemID(u32), create value=1, 0, durability(u16), zeros`）；`dnf_equipment_entry_extra` 写 `source=pvf_create_equipment_list`、`pvf_path`、`durability`、`max_durability`、`repair_gold=0`、`equipment_type=<.equ 中 [equipment type] 的尾随数字>`；武器强化写在 `ext_data0`。穿戴槽：武器 11、上衣 13、护肩 14、下装 15、鞋 16、腰带 17、项链 18、手镯 19、戒指 20、辅助 21、魔法石 22、耳环 23；时装直接使用外观槽 0..9 并把 `current_exe_equipment_type=<槽位>` 写入 extras（不要用 `source=pvf_create_equipment_list`，否则会走旧槽位映射）。
- 任务门禁：`dnf_quests`（父行）+ `dnf_quest_states(character_id, state_group, quest_id, status, ...)`（主键含 `state_group`，同一任务不能同时 completed/active）。服务端判定城区域准入用 `area.NeedQuests`（来自 `.twn` 的 `[need quest]` 段，不满足时报 `target_area_has_pvf_quest_requirement_without_completed_quest_owner`），完成状态取 `status ∈ complete/completed/cleared/finished/done`；选角 ACK 只投影 `status='active'` 的行。机器人写入 `state_group='states'` 即可。
- 宠物/生物（creature）持久化形状（与服务器 `pet.GrowthOwner.validateWornPetEntry` 对齐）：
  - `dnf_pets(character_id, equipped_key, town_display, updated_at)`：`equipped_key` = 十进制 serial，`town_display=1` 才在城镇显示。
  - `dnf_pet_entries(character_id, pet_key=serial 十进制, creature_key=serial, item_id, source_list_type, source_slot_index, pet_name, name_raw, satiety, satiety_micros, mode_flag, mode1_field_0a/b, pet_level, pet_exp, tail_flag, raw_entry)`：**穿戴中**的宠物必须 `source_list_type=3`（装备列表）、`source_slot_index=26`，且 `creature_key` 与 equipment 槽 26 行的 serial 一致；`name_raw` 留空时服务端会用 PVF 名称以 GB18030 投影。
  - 装备槽 26 行：46 字节 raw（`slot=26`、`+1 itemID`、`+5 serial`、`+24 serial` 重复），extras 建议带 `creature_serial_or_handle`/`creature_key`；不要写 `7:*` 背包行（穿戴中的宠物不在宠物背包里）。
  - `dnf_pet_artifacts(character_id, entry_key='red'|'blue'|'green', item_id, item_count, ...)` + `dnf_pet_artifact_extra`：已装备神器只存在这里（PetRecord.Artifacts），同样不占宠物背包格。
  - 宠物 `satiety`/`satiety_micros`（= `satiety * 1_000_000`）由服务端城镇/副本计时结算并回写；机器人写入初始 100 即可。
- PVF 列表解析：`equipment/equipment.lst` 是单行、id/路径对平铺，但存在缺失 id 的错位行；按固定步长配对会丢失尾部（90CN 的神器与约 1.7 万件装备）。解析器需在非 id/路径对时向后重同步。神器 `.equ` 的 `[equipment type]` 是 `` `[artifact red]` 15 `` 形式。
- 副职业摆摊协议（已实机取证）：
  - 开店 `op598`（legacy frame cmd=1 或 upper 均可命中同一 handler）：`u8 kind`（0=分解机、3=附魔摊）、`u32 名称长度`、名称（GBK 字节）、`u32 收费`、`i16 x`、`i16 y`、`u16 link`，总长必须等于 `15+名称长度`；成功回 `{1}`（upper msgID=598，classification=1），失败回 `{0, code}`。
  - 关店 `op600`：体为空；**成功不回 ACK**，向同区域广播 NOTI539（`u16 ownerID`，class=0，房主也会收到），只有失败才回 `{0, code}`。
  - 准入：角色 `expert_job_type`（`dnf_character_stats`，1=附魔师、3=分解师）匹配摊位种类；收费 ≤ PVF `limit store charge`（本机 10000）；机级/耐久取 `expert_job_machine_grade`/`expert_job_machine_endurance`，缺省时用 PVF 初值（机级 1、耐久 300）；不得在副本/队伍中。
  - 开店后服务端向同区域玩家广播 NOTI538（创建），附魔摊额外向房主发 NOTI544（更新）；同区域重登会收到 `replayCurrentExpertJobStores` 重放。
  - **场景就绪回执**：客户端必须在首个 op24 之后发送 legacy `type1345`（体为 4 字节 `02 00 00 00`），否则服务端一直挂起 `game-upper-select-character-scene-tail-deferred`（场景尾包/HUD/战斗力投影不下发），并且后续开店等城镇交互会被判为状态未就绪（失败码 19）。
- 写入时机：角色离线（未选角）。在线会话会整集合写回（背包/装备/宠物/任务），选角时服务端还会按 (job,grow,level) 重算并修复 `stat_*`。写库用独立连接并设置 `busy_timeout=5000`。
- 父行必须先存在（`dnf_inventories`/`dnf_equipments`/`dnf_pets`/`dnf_quests`/`dnf_skills`），否则服务端会用默认值回填。
- 管理 API（`X-Admin-Token`，危险操作需 `X-Admin-Confirm: POST <path>`）：`/local/profession-set`（job/grow/target_level）、`/local/equipment-move`（equip/unequip）、`/local/dungeon-control`、`/local/companion`、`/local/boss-modifier`、`/local/client-account`、`/local/shutdown`；没有金币/经验/发物品/建号 API。

## PVF 要点

- 90CN `Script.pvf` 是 protected_nkpi：字符串池键为 `StRa`/`StRw`（两个 u32 头 + protected keystream），body 用 `hEAd`/`grpi`/`bODy` 键。适配器 `pvf_archive.go` 已支持。
- 本机验证：1,057,913 路径、257 城镇区域、122,878 装备/装扮、45,584 可叠加、16 职业属性表、99 等级阈值、任务门禁 24/926。
- 与服务端算法差异（持久化阶段要对齐）：服务端属性向量只把 HP/MP/回复/速度/跳跃/重量乘 10，力量/智力/体力/精神/攻击/防御/独立/抗性保持原值；属性列还包含 `stat_level=100`、`initial_defaults` 的块标记 83 与 18 个 `active_status_resistance_*`；服务端选角时会按 PVF 重算并覆盖不一致的 `stat_*`。
- 职业映射需覆盖 11-15（at swordman/knight/demonic lancer/gun blader 等），当前 `capability/pvf/pvf_parse.go` 的 job 映射到 10 为止。
- 服务端角色属性算法在 `internal/modules/dnf/charstat`：`[initial value]` + `[growtype 1]`（≤14 级）+ `[growtype n]`（≤49 级）+ `[awakening n]`（≥50 级）+ 特权 HP+9800/MP+10500。
