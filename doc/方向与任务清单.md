# 方向与任务清单

日期：2026-10-17。依据 = 参考源代码库八棵树的清点（`G:\90-CN\reference\`，索引见 `reference\INDEX.md`）+ 本仓与服务端源码核对。

本文档回答两件事：**下一步做什么**，以及**哪些能在不动服务端、不动客户端的前提下做**。

## 0. 结论

本仓不是功能落后，是三条链路没接通。服务端能力远多于本仓已使用的部分 —— 例如「副本真刷图」这一整条链（报怪死 → 拾取 → 换房 → 结算）服务端早已实现，只是没有机器人从这头发包。参考库的价值不在"告诉我们该做什么"，而在"这些事别人已经实机验证过，照形状抄"。

## 1. 硬约束：不服务端 / 不动客户端的可行性

**分界线**：机器人是**另一个客户端**，能做的只有两件事 —— ① 发协议包；② 离线写 SQLite。凡是"改变发给真人客户端的内容"或"改变服务端领域规则"的事，机器人一概做不到。

### 环境差异：SQLite 不是短板

参考库里有 MySQL 的服务端与"真服务器"形态。本环境是 **SQLite 单文件**，对机器人而言这反而是**优势**：不需要凭据、不走网络，**直接写文件**即可（摆摊副职业、宠物、装备、清理都是这么做的）。

唯一需要守的纪律是 **SQLite 单写者**：与运行中的服务端并发写会 `SQLITE_BUSY`。P1 的疲劳写入是**低频**（换日一次、每房间一次），不构成热点；批量写入仍须走既有离线写入通道（在线门控 + 重登），不得裸写。

## 3. 我们的位置：有超出，也有缺口

**本仓已有、S4A21 至今没做的**：拍卖行、邮件收信（已实机验证零丢失）、物品交易、同区私聊、组队进副本、表情、死亡/复活、宠物。

**S4A21 有、本仓没有的**：分解机 / 附魔师摆摊（1200 在线实机）、**物品触发的全服公告**（开箱 / 强化，不依赖服务端改动）、公会邀请自动同意、转职 / 觉醒离线写入、任务门禁清空、角色属性按服务端算法重算对齐。

**两边都没有、且已双向判死的**：副本内跟随。S4A21 `doc/优化与跟随规划.md:96` 与我们结论一致 —— 客户端**不处理成员的 UDP 位置帧**，服务端也不向副本内队员投影位置。**不要再重开。**

## 4. 本轮关键发现

### 4.1 副本"真打"服务端已就绪，只差机器人发包

战斗是**客户端权威**：`dnfbridge\dungeon_monster_runtime.go:36-54` 的怪物运行结构里**没有 HP 字段**。完整链已实现：

| 环节 | 包 | 服务端落点 |
|---|---|---|
| 报怪死 | `op39 DieMonster`（带 RuntimeObjectKey / OwnerObjectKey / CombatState） | `dungeon_combat_runtime.go`（经验累积、击杀计数、掉落） |
| 拾取 | `op44 GetItem` | `dungeoncmd\handler.go` |
| 换房 | `op45 MoveMap`（100 B） | 同上；**疲劳在此按房间扣**（`dungeon_combat_runtime.go:463`） |
| 结算 | `op46 SetPlayResult`（8 或 16 B） | 同上 |

⚠️ **修正旧结论**：先前记录的"op45 需要先清房"是错的 —— **清房就是客户端报怪死**，是同一件事。

### 4.2 疲劳值是唯一拦路石

本服务端强制校验：疲劳属性缺失直接 `ErrEntryFatigueUnknown` 拒绝入场（`modules\dnf\dungeon\runtime_policy.go:12-61`）；上限 156/天、**06:00（UTC+8）换日**、按房间在 `op45` 路径扣减。

活库里 301 台机器人**全是 0 消耗**。⚠️ 但它们现在确实进得了副本（A1-7 实测 122 次进本），说明走的是**免疲劳口** —— 该口是哪条路**未验证**。最便宜的判据 = 查它们进入的那张图的 PVF 疲劳字段，一条查询结案。

本仓目前与疲劳相关的代码只有一处：`internal\protocol\cn90\dungeon.go:38` 的 `0x16: "fatigue exhausted"` 文案。

### 4.3 决斗场是参考库都没有的独有资产

本服务端 `dnfbridge\gameplay_module_joust.go:28-69` 有活的 `joust` 模块（info / betting / history 三个 opcode）+ `pvp`（arcade / practice）。S4A21 全树没有；轮回的"无双竞技场"有实机证据。这是**最像真人、规则又最明确**的场景（不需要真打怪）。

### 4.4 16ww 与本服务端同族，可直接 diff

`ServerS5A3-16ww` 的 `go-server\internal\{services\dnfbridge, modules\dnf, app\dnf90, services\logic\dnf}` 与本服务端目录**完全同构**，且同样有 `party_online.go` ⇒ **可逐文件 diff**，是本轮最便宜的一条取证手段。

⚠️ 但它的 op9 布局绑定的是**它自己的客户端档位**（地址族 `sub_1D64CA0` 等），与我们的 `01C1672E` 不同 —— **队伍包布局不得直接抄**，闸门逻辑与"画框三件套"可以。

### 4.5 武器被卸：建议重开 A2-1

16ww `更新日志.md:16` 把它列为**玩家反馈、高优先在修**：

> 持有光剑、扫把、拳套等**有掌握技能要求**的武器进入城镇区域时，会导致该区域**其他角色**的武器被卸下。

这正是本仓已封板的「武器被卸（洪峰）」。封板结论是"客户端自己发 op19、服务端无罪、不削"；16ww 给的是**服务端侧根因 = 掌握技能要求**。

⇒ 若成立，修法不是"削洪峰"，而是"**假人别发没掌握技能的武器**（或把对应技能写进存档）" —— **纯机器人侧可解**。**未验证，属同区线索**；查法：统计机器人武器池里带掌握技能要求的件数 + 存档里有无对应技能。
