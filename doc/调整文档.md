# 调整文档

本文档记录本周期（审计修复 / 性能优化 / 交互治理 / 跟随规划）对配置、数据与运维方式有影响的调整。按阶段提交，提交信息见各条末尾的短哈希（以 `git log` 为准）。

## 数据修复（启动时自动执行）

- **战斗属性与经验**：写入等级时同事务写入 `character/ExpTable.tbl` 的累计经验阈值，并按 `.chr` 成长表重算 `character_subtype1_fields.stat_*`。存量机器人在启动对账时补齐。
- **成长对账**：未转职、未开放分支或损坏的 `grow_type` 会按 PVF 重新选择；已转职角色的觉醒档位在 `reconcile_awakening=true` 时补齐。对账失败不再中止启动。
- **任务门禁**：启动时清空并重写固定门禁集合（世界地图持久门禁标记完成，`[in progress]`、地城 `[quest connection]` 与 `[dungeon info]` 反向引用任务保持进行中）。
- **装备/装扮/宠物对账**：负载只有在校验窗口不满足时才重写（等级窗口、成套、职业、宠物/神器窗口）。修复后同一份数据库重复启动不再改写，已实测幂等。
- **启动清理**：仅处理名为 `前缀+UID` 且在 `robot_uid_start..robot_uid_end` 内的账号；账号不是完整可用角色时整账号删除（含全部角色）。删除前会在短事务内复核候选未变化。

| `CN90_PARTY_UDP_REGISTERED` / `CN90_PARTY_UDP_REGISTER_FAILED` | 会话开好后绑定队伍 P2P UDP 口并向服务端上报端点（31 字节 class1/op2）。`REGISTERED` 带 `cid=` 与 `port=`；`_FAILED` 表示绑口或上报失败，该会话的队友行会一直停在「连接中」 |

## 行为变化

- **发行包首次启动直接继承 `config.ini`，不再被恢复页重置（2026-10-17）**：此前空白的 `state/backend_selection.json` 会让启动流程认为「后端未配置」，跳恢复页；恢复页写回设置时把 `config_generation` 加 1，随后 `PrepareBackendRuntime` 判定为一次显式切换，把发行包自带的调优 `conf/robot_config.ini` 连同 `state/logs/tmp` 一起移进 `config.backend-bak.*`，再用内嵌默认值重写——玩家首次启动即丢掉全部测试配置。现在启动路径先用 `config.ini`（`ServerDirectory` / `RobotConnectIp` / `Game`）补齐选择里的缺失字段（`cmd/robot/backend_settings.go` `fillBackendSelectionSettings`），补出的选择保持 generation 0 并持久化，恢复页不再出现，`PrepareBackendRuntime` 也不会搬走配置。轻量发行包模板的 `config.ini` 同时改为 `ServerDirectory = ..\Server-90`：从 `Robot\` 直接双击 `robot.exe` 时按相对路径自动找到同级的服务端目录；`启动全部.bat` 仍把它改写成 `%ROOT%\Server-90` 绝对路径。
- **工作台「自动」对话框在全部能力已启用时不再崩溃（2026-10-17）**：`autoCapabilitySwitchControls` 的禁用分支在 `missing` 为 `undefined`（所有能力都已启用，发行包现场即如此）时仍去读 `missing.reason`，抛出 `Cannot read properties of undefined (reading 'reason')`，整个对话框打不开。三元分支已对调，只有真的缺能力时才生成 `disabled` 与提示。
- **切图以服务端的回复为准，不再以自己请求的那张图为准**：切图请求此前只认「回复恰好等于请求」这一种结果，其余一律当失败并把请求的城留作已知位置。可服务端不是这样回答的——共用门厅（38/1）没有直达外村的传送门，请求离开它会被改成**门厅自己的出口**；被路线守卫拒掉的请求则什么都不回。两种情况下机器人都会继续以为自己还站在门厅里，之后每一步都从一张已经离开的图发起，这就是线上「想走走不掉」的形状：摆摊轮次会把每个机器人重新上线一次，而每次登录都落在那个门厅。现在会话记下服务端通告的那次落地（**不等于请求也记**），按角色 key 过滤掉队友的切图通知，每次会话最多打 8 行诊断；传输层在切图失败后读这条观测，改写自己的位置与 `locationKnown`，下一步从真实位置发起（robot `c324d19`）。

- **站在「目录不认的图」里的机器人从自己的门走出去，而不是原地打转**：`AutoMove` 在没有跟随目标、也没有钉死出生点时，此前一律把目标设成**当前所在地图**——对一张 `use=false`、没有矩形的门厅图（服务端每次角色列表登录都会开的那张共用赛丽亚房间 38/1）来说，这就是永远在房间里绕圈、从不请求离开。线上实测该房间堆了 137/300 台，且还在涨。现在这类机器人改为从**自己这张图的传送门表**里挑一个门作为目标：门仍需过目录（`use=true`、等级不高于机器人、有移动矩形）与人群策略两道过滤，全不合格时退回原来的原地游走。选目标只用自己的门，是因为服务端只为它证明过的路线放行——目标若取自整个世界，就可能是一张当前城镇根本没有路线的场景，那种请求被静默丢弃（摆摊轮次就是这样把整轮重试预算烧在了 98 村上，6/94 轮）（robot `25bae68`）。
- **登录落地位置按「服务端实际开的场景」记账，不再按请求的愿望**：`seedLoginLocation` 先问会话 `LoginLanding()`（登录序列里 `loginObserver` 顺手收下的 0x0017 通知），拿不到才回退到请求值。此前把愿望（`InitialTown*`）写成已知位置，于是同一个城内的移动会被当成**裸位置上报**（发向一个角色并不在的场景），后续每次跨城传送请求也都会报错源城。线上实测：请求 `98/23`、`18/3`、`98/22` 的角色，服务端一律开在门厅 `38/1/450,234`——记成愿望之后它们再也走不出去。记成观测值之后，`AutoMove` 发现自己在 38/1 而目标是别处，就会发**区域切换请求**（门），这才是把机器人带出门厅的那条路（robot `d075085`+）。
- **新增「假人组队进副本」一整条线（默认关）**：`auto_party_dungeon=true` 后，机器人会**先在这张图上招人、再作为队长带队进副本**——`AutoPartyDungeonEnter` 从同村同图的机队里挑 `_size-1` 个候选（排除摊位机器人、已有队伍的、以及别的角色 id），逐个发 op10 mode13 邀请，然后在 `_invite_timeout_sec` 窗口里等名册；等到的成员数 ≥2 就由队长发 op16，服务端做完全员校验（在线、同队同队长、同区域、落地就绪）后把**跟随者一起拉进副本**，跟随者收不到 op16 回执，他们收的是 class0 的 op27/28/29。窗口里一个人都没答应、或入场被拒时，队长发 op13 把自己的队伍解散，本轮按 `party_not_formed` / 入场失败记账。
- **退出副本是一条统一的「值班」而不是队长的收尾动作**：服务端**不会**在队长离开副本时把队员一起带出来，每个成员都得自己走自己的路，所以机队多了一条 15–30 秒一跳的 `party_exit` 轮次（比其它自动动作密一个数量级，因为它是唯一能救「被困在副本里」这种状态的轮次）：先看 `_dwell_sec` 停留是否满了，满了就退副本、再退队伍。这条路同时兜住了另一件事——`AutoDungeonEnter` 在「入场成功但收尾失败」时会把机器人留在副本里，以前没人管，现在到点自动出来。
- **退队伍用 op13（`CmdLeaveParty`），不用踢人**：服务端接受**任何成员**发来的 op13、忽略包体、回一字节确认并把名册推成空，是唯一不需要「队长身份」的退队方式（踢人 op14 只认队长，且它的槽位字节是**收件人自己投影里的行号**，不是全局槽位号，按它踢人不可靠）。所以「队伍成型后没人进副本」这种死局是**每个成员各退各的**，而不是队长替全队解散——队长带人退队时服务端会把队伍**改组成继任队长**，剩下的人仍在队里。
- **只有「全是我们自己机器人」的队伍才会被强制拆散**：散队守卫要求队伍里每个角色 id 都能在机队状态里找到，且队伍已经站过 `partyFormationGrace`（90 秒，必须长过集合窗口）。队里只要有一个不是机队的角色（真人玩家的队伍），机队就**不碰**，代价写在代码注释里：这种情况下可能有一队机器人一直站着，直到需求层把它们回收。
- **组队开关要求两个能力同时具备**：`party` + `dungeon_enter`。缺任一个，配置策略会把 `auto_party_dungeon` 清成 `false`（`applyBackendConfigPolicy`），网页上的勾选框也随之禁用——否则面板会宣传一个后端服务不了的功能。
- **副本真刷图（`auto_dungeon_clear`，默认关；2026-10-17 已实现，同日实机验证）**：服务端不保存怪的血量，一房怪「死」= 客户端用 op39 把这一房 actor 全部报死；走房 = op45 请求一个**曼哈顿相邻**坐标，服务端从自己的迷宫拓扑规划并回一条新 op29。**迷宫布局从不下发**，而且被拒的换房请求**完全不回包**——所以走法是深度优先：每进一房先把 `op29 actor 行` 里 `Blocking==0 && Type!=4` 的怪逐个报死，有 boss（Type 3/8）则 op117 死检（服务端回 op115 + 无体 op31；op31 实际在 boss 的 op39 报死时就已推送，早于 op117），op31 结算入口由每会话的结算 worker 按 `op46→op123→op69→op70` 应答（op46 为 42 字节全 0，服务端只判形）；否则按固定顺序（右/左/下/上）试四个邻格，`2s` 内没有匹配坐标的新 op29 就把该格当墙，四邻全试完回退父房（已证明可走）。预算 80 步 / 6 分钟。只有队长走——服务端在每个换房被受理时自己移动队员并投影死亡。日志：`CN90_DUNGEON_CLEAR_START/ROOM/ROOM_KILLED/WALL/BOSS_CHECK/CLEARED`。
- **退场值班必须排在「队伍活跃即返回」的守卫之前（2026-10-16 修复，`584c165`）**：`Actor.tick` 在机器人处于活跃队伍时直接 `clearAutoActionSchedule(); return`，而退场值班（15–30 秒一跳）原本在那条守卫之下，于是「进本 → 退本 → 退队」的整个后半程从来不会发生——首日现场 28 轮组队进副本之后，约 84 台机器人（队长+跟班）进本即永久静默、`party_exit` 一条都没有。现在它提到守卫之前，并自带 `modeValue()==ModeAuto && AutoActionsEnabled(rc)` 门控；它因此是**队伍中仍会跑的自动动作之一**（2026-10-17 起还有 `party_follow`，见下条），正是 `AutoPartyDungeonEnter` 注释所依赖的行为（"让成员靠 `AutoPartyDungeonExit` 自己走出来"）。教训：这条链路的日志在"值班根本没跑"和"值班跑了但被静默取消"两种情况下**都是空的**，排查时应先核对守卫顺序，而不是先怀疑包。
- **城镇组队跟随是一条独立值班，和退场值班一样排在队伍守卫之前（2026-10-17 修复，实机复现「城镇里假人不跟人走」）**：队伍守卫把整个单人行动轮（喝水/喊话/摆摊/随走）挡在外面，而跟随以前只存在于单人随走轮里，于是被真人邀请进队的假人虽然一直在收队长的 `NotiUserPosition`（日志 `CN90_PARTY_FOLLOW_POSITION … COLOCATED`），却一步都不走——现场有人无法把假人带进副本。现在 `party_follow` 值班每 3–6 秒调一次 `AutoMove`：有队长坐标就走过去（落点在跟随半径内），没有就站着等（`ActionStateOffline`），在副本里做（`DungeonState` 活跃）则直接取消记 `in_dungeon`、不发任何城镇移动——否则队伍整段停留期间每个跟班都在朝城镇要路。每个会话每次入队最多打一行 `[Actor] party_follow`，失败打 `party_follow_failed message=…`；摊位机器人（`RobotType` 2/3）不跑跟随值班，免得被走离摆摊点。
- **副本换房以玩家为准，假人进房按真人节奏打怪（2026-10-17 实现，未实机验证）**：原版 DNF 要求全队站门口读倒计时才换房；我们这套不走那条规则——队长（真人或队长的自动刷图）op45 一经服务端受理，服务端自己把每名队员搬进下一房并各推一条 op29，所以**玩家穿门零延迟**，跟班不需要任何站门口的协同。跟班侧新增 `startDungeonFollowDuty`（随 `startDungeonTracking` 一起装，和结算 worker 同款队列 worker）：每收到一次属于自己副本的房间投影，把该房里所有阻塞 actor（`Blocking==0 && Type!=4`，**boss 与敌对 AI/APC boss 一并打**）逐条 op39 报死，重复投影不重报（按 object key 去重、按副本 `since` 重置）。**节奏刻意做成真人尺度**：进房先等 0.9–1.8 秒接敌，普通怪每只 1.4–3 秒，boss 战 22–40 秒；旧版「投影一到整房瞬清」会在真人还在读条时清完房，把击杀与掉落记到假人头上（2026-10-17 现场：真人杀的 5 只被服务端记成 cid 432 的击杀）。用户 2026-10-17 口径：「假人在副本里战斗的最终表现类似于真人玩家，真人玩家能干什么他就能干什么」——boss/精英/APC 不再排除。判据 `dungeonState.followed` = 见过 op28/op29 但从未见过 op16 回执，队长侧因此继续只走 `ClearDungeon`，两套走路者不会在同一本上重复报死。日志 `CN90_DUNGEON_FOLLOWED` / `CN90_DUNGEON_FOLLOW_ROOM` / `CN90_DUNGEON_FOLLOW_KILL` / `_KILL_FAILED`。单测覆盖：全员含 boss 都打、队长自己的本不插手、同房重复投影只报一次、退本后不再报。**未验证**：待真人带假人连进两房实机复验。
- **退出值班的两条新裁决（2026-10-17，实现，未实机验证）**：`AutoPartyDungeonExit` 原本只认「全员本机机队」的队伍，其余一律等 dwell——真人拉队时假人进不了这个分支。现在加两条覆盖规则（都只放宽退出，不放宽散队）：①**通关后**（`DungeonSettled`，即已收到 op31 结算入口）里，已结算的副本不属于任何人，dwell 与「外人是队长」两道守卫都不再生效，假人发 op42 退本回城；但队伍**不散**——花名册里还有真人时照旧记 `party_foreign` 留着队伍，假人因此与真人一起回城、队伍保持。②**真人退出了队伍**：退场值班把「上一跳非本机机队成员」与「这一跳从花名册消失」做名册对名册比较（`notePartyForeign`），只有**消失**才算真人走了——短暂掉线的本机成员仍留在服务端名册里，不会误判。真人一走，队伍与副本都归机队，dwell 与组队宽限期立即跳过，假人退本并退队，站回副本门口。日志沿用 `[Actor] party_exit … message=`（`dungeon_exited` / `party_left members=N dungeon=true`）。
