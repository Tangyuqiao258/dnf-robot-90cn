1. **op16 之前没有 op15 就被静默丢弃**（非教学本），而 op15 能绑住回城原点靠的是当前城镇场景里**有一次 op35 上报**（只有 op35 的 handler 写那个 `PositionValid`；登录时的 op36 是场景切换、不写）。缺失时的表现同样是静默丢弃——这一点在死亡/复活那条已经踩过，本次直接沿用同一套原点重报。
2. **op16 的 ack 只说明副本跑起来了，class0/op37 才说明场景加载完**。服务端在收到 op37 之前会扣住角色状态推送、技能帧与房间放置，所以只做到 op16 ack 的实现在服务端看是"角色卡在一个从未加载完的副本里"。op37 服务端**只按长度判定、一个字段都不解**。
3. **房间移动（op45）本次不做**：op45 是恰好 100 字节明文，只读 `NextX`/`NextY`/`MoveKind`，但要求**目标房间曼哈顿相邻且当前房间已清空**——清空要战斗，本版本没有；且迷宫布局**不在协议里**（op28 只给 DungeonID/Difficulty/MazeIndex/BossX/BossY，op29 给当前房间自己的格坐标），房间图只有读 PVF 才知道。所以"能进副本"的交付边界 = **进得去、站得住、退得出**，`CapabilityDungeonMove` 保持关闭。

**实现**：协议层 `FinishLoading`/`GiveUpDungeon`；会话层 `EnterDungeon`（op35/op15/op16 之后接 `finishDungeonLoading`，`DungeonLoaded()` 为真才算走完）与 `LeaveDungeon`（发 op42 等 class0/op24 城镇切换，且**没有进行中副本时先拒绝而不发**——服务端对城里的 op42 同样静默丢弃，发了只会把"一次注定被丢弃的请求"报成超时）；actor 回合 `AutoDungeonEnter`。

**回合是整段往返，不是只进不出**：没有任何适配器会驱动角色在副本里做事，停在副本里的机器人会让其余所有自动动作（移动/摆摊/拍卖/邮件）以为人在城镇。所以 `AutoDungeonEnter` = 进 → 确认加载 → 主动放弃回城。

**开关**：`auto_dungeon_enter`（**默认关**，受新增的 `CapabilityDungeonEnter` 门控——与 `CapabilityDungeonRevive` **分开**：能应答死亡通知不等于能开一次副本）。默认关的理由：它是唯一会往角色身上真正提交一次副本记录的开关，而且 dungeon id 属于各服务端自己的 PVF，默认全机群开等于把每台机器人送去"id 3 恰好是什么"。配套 `auto_dungeon_enter_id`（默认 3 = `Act1/MirkWood.dgn`，lab PVF 门槛最低）、`auto_dungeon_enter_difficulty`、`auto_dungeon_enter_interval_min/max_sec`（默认 600..1800，下限钳到 60）。同批接入 Web 自动设置对话框与 `applyBackendConfigPolicy` 的清零清单（`backend_config_policy_test.go` 的表已加行）。

**实机验证（lab，`TestLiveDungeonEnterAndReturn`）**：robot17000016 在**一次会话里连续两次**往返（进 → `DungeonLoaded` → 退 → 再进 → 再退），第二次专门验证城镇场景在第一次退出后已被重建、会话必须重新绑一次原点。服务端 `packet_log.txt` 独立佐证：`game-dungeon-runtime-prepared dungeon_id=3 maze_index=0 room=0:1 map_id=58548 map_path=map/Mirkwood/Mirkwood1.map monsters=4` → `game-upper-finish-loading-status-send request_body_len=8` → `game-main-post-finish-loading-player-state-send source=request37_after_upper_status_after_finish_loading_state` → `msg_id=42 ENUM_CMDPACKET_GIVEUP_GAME plain_body_len=0` → `game-dungeon-back-to-village-op24-send request_msg_id=42 response_msg_id=24 town_id=38 area_id=1 position_source=current_exe_op35_runtime_origin_snapshot`。整段服务端耗时约 57ms。

**仍未做**：副本内跟随（阶段六已放弃）；副本内房间移动（需战斗 + 读 PVF 迷宫图）；副本内其它动作（拾取/技能/通关结算）。

**全量实机盘（2026-10-14 上午，lab）**：`CN90_LIVE_PROTOCOL=1` 跑完 `internal/composition/backend/cn90` 整包 —— **179 passed / 0 failed / 12 skipped**（跳过的 12 条全是需要 `CN90_LIVE_PURGE`/`CN90_LIVE_REDISTRIBUTE`/`CN90_LIVE_STORE` 等额外开关的重型用例，默认跳过）。七条 live 用例全绿：`TestLiveSameAreaChat`、`TestLiveChatToAnAbsentCharacterIsDropped`、`TestLiveDungeonDeathRevive`、`TestLiveDungeonEnterAndReturn`、`TestLiveDungeonDeathInTownIsDropped`、`TestLiveEmote`、`TestLivePartyFollow`。其中 `TestLiveDungeonEnterAndReturn` 本次以 cid=277 重跑，服务端 `packet_log.txt` 独立印证整条链（`select_dungeon_after_op29_commit` → `game-main-finish-loading-state-send msg_id=37 classification=0 body_len=87 source=request37_after_upper_status` → `game-dungeon-back-to-village-op24-send request_msg_id=42 response_msg_id=24 dungeon_id=3 room=0:1` → `game-delete-success character_id=277`）。用例本身 0.06s —— 本机全本地且服务端已热，不是"跳过了"（上方逐条日志 `session online`/`scene loaded`/`character returned to town`/`second round trip completed`/`test character removed` 都在）。

**顺带修掉一处既有不稳定（非本次引入；已定案并修复）**：`TestLiveRobotProvisionAndSession` 隔离重复跑时约 1/6 概率失败于 `live pet parent: sql: no rows in result set`。

- **根因（读源码定案，非猜测）**：`pets.go:86` 的 `applyRobotPet` 有一道概率闸门——`PetProbabilityPercent < 100` 时按 `cn90DeterministicPercent(character_id)`（`character_id` 字符串的 FNV-32a % 100）跳过整只宠物，目的是"机器人重启不要重新掷骰"。而 `robotconfig.Default()` 是 **80**（`defaults.go:18`），于是**约 20% 的角色 id 根本不写宠物行**。这个用例每跑一次都要先删号再建号，服务端每次发新的 `character_id`，"稳定"的哈希也就每跑一次重掷一次——**20% ≈ 实测的 1/6**。用例用的是未经修改的 `robotconfig.Default()`，是整个包里唯一没把该值置 100 的调用方（`pets_test.go` 四处都置了 100，理由相同）。
- **双向验证**：① 把该值临时改成 **0**（强制必跳）→ 一次即复现出**同一条**报错 `live_protocol_test.go:173: live pet parent: sql: no rows in result set`，链路坐实；② 改回 **100** → **连跑 8 次全绿**（改前该值下的期望失败率 ~21%，8 连绿的概率约 15%，且 ①的按需复现已确定性证明因果）。另用 FNV-32a 独立复算 id 100..199 区间：**21/100 = 21%** 落在跳过集，且本会话服务端实际发过的 `character_id=138`、`161` 都在集合内。
- **修法**：用例里显式 `applier.Config.PetProbabilityPercent = 100` 后再 `InitializeCharacter`。这不是"绕过断言"——被断言的正是宠物写入器写出的行形状，而那道概率闸门是它**故意**不写的分支，闸门本身已有单测覆盖。
- **另一处（澄清，非缺陷）**：`自动机器人甲`/`乙` 被多个 live 用例共用，而服务端角色名是全局的。读 `provision.go:203-231` 可知：名字被占时 `provisionCharacterNameCandidates` 会退到随机后缀名**继续建号**，不是失败；`TestLiveRobotProvisionAndSession` 也从不比对"请求名 == 结果名"（只 log，后续一律沿用 `result.CharacterName`）。所以这是噪音不是 flake——先前把它记成"谁后跑谁背锅的假 flake"是**错的**，此处更正。本次新增的实机用例仍单独占用 `robot17000016`，避免这类噪音。
